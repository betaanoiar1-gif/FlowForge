# Public Feature Matrix: Google Flow Automator, GA Studio, and Google Flow

- **Research checked:** 2026-10-04
- **Scope:** Public Chrome Web Store listing/release notes, the publisher's user guide, and Google's public Flow Help Center. This is behavioral/product research only. No extension source, hidden endpoints, private APIs, DOM selectors, credentials, or access controls were inspected or reverse engineered.
- **Implementation-status note:** Public-source observations remain unchanged. Implementation cells now reflect Phases 1–4C plus Phase 5 (plan materialization into durable execution); see [ARCHITECTURE.md](./ARCHITECTURE.md), [docs/vertical-slice.md](./docs/vertical-slice.md), [docs/google-flow-provider.md](./docs/google-flow-provider.md), [docs/application-services.md](./docs/application-services.md), and [docs/plan-execution.md](./docs/plan-execution.md). Phase 2 browser/provider behavior is fake-tested only; live Flow behavior is **BLOCKED / NOT RUN**. Phase 6 hardened that provider's *execution boundary* — one Generate submission per attempt enforced by the durable recovery record, mandatory pre-click prompt verification, a state taxonomy that separates a loading page from a missing editor, prompt input, or Generate control, fail-closed correlation, artifact describability before handoff, and a recovery classification that defers the same attempt whenever a remote generation might exist — proven entirely against a fake `BrowserGateway` (50 new tests asserting side-effect counters). It adds no Google-specific engine, queue, worker, retry engine, or asset store, and it validates nothing about Google's live page. Phase 3 adds the application-service layer and operator CLI commands (queue inspection/run, review, selection, readiness); it adds no web UI, no reordering surface, and no live Flow validation. Phase 4A adds the creative planning domain — durable creative briefs, versioned production plans with story/cast/world/Visual-DNA/scene-plan/generation-spec data, deterministic structural validation, and provider-capability gating with an execution preview — and adds no planner, no LLM call, no autonomous submission, and no new provider capability. Phase 4B adds the deterministic planner engine — a pure, versioned 12-rule registry that turns a brief and explicit planning input into a validated plan version with derived identifiers and write-once provenance — and adds no LLM call, no agent, no provider call, no queue submission, and no command that executes a plan (see [docs/planner-engine.md](./docs/planner-engine.md)). Phase 4C adds the **AI planner adapter**: a provider-neutral `AIPlanner` port whose structured proposal is schema-validated, normalized into planner input, and authored by the same 4B rules under the same 4A gates, with write-once AI provenance, dry run, an explicit deterministic fallback, and one CLI verb (see [docs/ai-planning.md](./docs/ai-planning.md)). It adds no agent loop, no tool-calling, no autonomous submission, no provider-implementation change, and no execution path; and no build, typecheck, test, or vertical-slice run in this repository requires a model credential. Google Flow Automator is a third-party browser extension; its advertised features are not Google product guarantees.

GoogleFlowProvider implements a fake-tested single-image/default-settings path only; video and other settings are rejected. The live UI path is unverified. |

| Storyboard and scene planning | Automator advertises storyboard planning and its release notes mention storyboard UI/UX changes. Google's public help documents Scenebuilder for arranging, reordering, trimming, previewing, and downloading a sequence of clips. These are related but not the same claim: the reviewed Google docs do not establish that Automator's planning UI is a Google storyboard API. [Automator listing](https://chromewebstore.google.com/detail/google-flow-automator-nan/jincmbkbdocdfgljlmoididhodhenbgm), [Google scene builder guide](https://support.google.com/flow/answer/16935718?hl=en&co=GENIE.Platform%3DDesktop) | Keep storyboard as structured FlowForge data: narrative beat, duration, location, characters, shots, camera/action, prompts, explicit references, and continuity constraints. Do not confuse a provider clip sequence with the canonical storyboard. | Structured planning data is implemented in Phase 4A: a versioned `ProductionPlan` carries `PlanStory`, cast, world and Visual DNA references, ordered `ScenePlan`s (narrative purpose, duration target, continuity constraints, planned outputs), and provider-neutral `GenerationSpec`s, all validated deterministically before approval. A planner now exists: Phase 4B's deterministic engine (`runPlanner`, 12 named rules) authors that structure from a brief plus explicit story/cast/world/DNA input, with derived identifiers, canonical normalization, input/output fingerprints, and version provenance — deterministically, so the same input always yields the same plan. Phase 4C supplied the *model-backed* adapter: `flowforge planner ai-run` asks an `AIPlanner` implementation (the domain port; `providers/openai-chat` ships as the reference one) for a versioned `PlanningProposal`, refuses anything malformed or unresolvable against the project's own facts, and hands the accepted proposal to the same deterministic engine through the same services — a model may propose beats, ordering, duration intent, cast, worlds, DNA, generation intent, and continuity, and decides nothing else. AI provenance (adapter, provider, model, schema version, path, fallback, and three digests) is recorded write-once outside the plan's content hash; prompts and credentials are never persisted. | Generation detection and timeout | Automator's guide explicitly notes a queue timeout can occur while Flow is still generating and a delayed page update can make status appear stale. It advises waiting, refreshing/rescanning, and retrying only the failed item. [Automator guide](https://googleautomator.com/user-guide) | Separate submission, provider monitoring, result detection, download, and validation. Treat “unknown” as ambiguous; inspect/recover before resubmission. | Durable attempts and same-attempt recovery exist. GoogleFlowProvider uses a local request-key manifest and strict visible prompt/media correlation; ambiguous UI state raises `submissionUnknown` rather than resubmitting. Since Phase 6 the monitoring states are separately named: `FLOW_PAGE_NOT_READY` (wait), `FLOW_EDITOR_NOT_FOUND` / `FLOW_PROMPT_INPUT_NOT_FOUND` / `FLOW_GENERATE_CONTROL_NOT_FOUND` (inspect, fail fast before any click), `FLOW_SUBMISSION_FAILED` (provably not submitted) versus `FLOW_SUBMISSION_UNKNOWN` (may be submitted), and an `attemptState()` phase that distinguishes `SUBMISSION_ACCEPTED` from `RESULT_DETECTED`. Fake-tested only; live Flow correlation is BLOCKED / NOT RUN. |
| Retry, delay, and blocked states | Automator advertises configurable/randomized delays and automatic retries. Its guide describes manual Retry Unfinished, and a pause/cooldown after repeated server-side “unusual activity” blocks, stopping if the restriction recurs. [Automator listing](https://chromewebstore.google.com/detail/google-flow-automator-nan/jincmbkbdocdfgljlmoididhodhenbgm), [guide](https://googleautomator.com/user-guide) | Classify failure before choosing recovery. GoogleFlowProvider reports visible auth/block status and does not bypass or evade challenges. ## Architectural patterns adopted (not copied)

1. **Queue work as durable items:** one prompt/scene operation has an identity, order, status, retry history, and inspectable result.
2. **Separate planning from execution:** a structured creative plan becomes typed scene/version records; a provider only executes a request. Implemented as a boundary in Phase 4A and hardened in 4B: creating a scene plan or a generation spec never creates a job, planning is a pure function over explicit input, and the only bridge to execution is the existing Phase 3 command path — `mapPlanToJobs` emits those commands as intents and submits none of them. Phase 4C keeps that boundary intact: a model may propose planner input, never submitted work. That own phase arrived as **Phase 5**: `plan execute` materializes an `EXECUTABLE` version — from either planning route — into scenes, scene versions, jobs, and queue items in one idempotent transaction, and stops there; the existing queue, worker, provider port, QC, and review path still do the executing, and no planning or planner command submits anything.
3. **Model references explicitly:** character/world/scene/shot/prompt references are data with version pins, not prompt text conventions alone.
4. **Observe provider state before retrying:** asynchronous generation and delayed UI updates make blind retries unsafe.
5. **Treat download/validation as distinct stages:** acquisition can fail after generation succeeds; keep recovery local to that stage.
6. **Make user review authoritative:** provider output is a candidate, not an accepted final asset.
7. **Isolate provider behavior:** Google Flow is an adapter behind capabilities and browser operations, so a mock, local model, or API provider can be substituted.
8. **Preserve the safety boundary:** use only authorized, user-controlled browser workflows and stop on security/access-control challenges.
